## 1. 왜 에이전트 관리 플랫폼이 필요한가?

요즘 개발팀에서 코딩 에이전트(AI가 코드를 직접 작성하고 수정하는 도구)를 하나쯤은 사용하고 계실 것입니다. Claude Code, Codex, Cursor Agent 같은 것들입니다. 그런데 에이전트가 한두 개일 때는 괜찮지만, 여러 개를 동시에 돌리기 시작하면 문제가 생깁니다.

- 누가 어떤 작업을 하고 있는지
- 어디서 막혔는지
- 이전에 해결한 방법을 다른 에이전트도 알고 있는지

사람 팀원이라면 슬랙에서 물어보면 되지만, AI 에이전트에게는 그런 협업 인프라가 없었습니다.

[Multica](https://github.com/multica-ai/multica)는 이 문제를 정면으로 다루는 오픈소스 프로젝트입니다. 코딩 에이전트를 사람 팀원처럼 이슈 보드에 올리고, 작업을 할당하고, 진행 상황을 추적하고, 한번 풀었던 문제를 재사용 가능한 스킬로 축적하게 해줍니다. GitHub에서 이미 16,000개 이상의 스타를 받으며 빠르게 주목받고 있습니다.

## 3. 에이전트를 팀원으로 등록한다

Multica의 출발점은 간단한 발상의 전환입니다. 에이전트를 도구가 아니라 팀원으로 취급하자는 것입니다.

### 기존 방식의 한계

기존 방식을 떠올려 보겠습니다. 개발자가 터미널을 열고, 프롬프트를 복사 붙여넣기 하고, 에이전트가 작업하는 동안 결과를 기다리고, 완료되면 다음 작업을 또 수동으로 넘깁니다. 에이전트 하나를 쓸 때는 이래도 괜찮습니다. 하지만 팀에서 여러 에이전트를 동시에 돌리면 상황이 달라집니다.

- 누가 어떤 작업 중인지 파악하기 어렵습니다
- 어디서 막혔는지 알 수 없습니다
- 같은 파일을 두 에이전트가 건드리고 있지는 않은지 확인하기 어렵습니다

### Multica의 접근 방식

Multica에서는 에이전트가 프로필을 갖습니다. 이슈 보드의 담당자 드롭다운에 사람 이름과 에이전트 이름이 나란히 나타납니다. 이슈를 에이전트에게 할당하면 다음과 같이 진행됩니다.

```
claim(작업 가져가기) → start(실행) → complete/fail(완료 또는 실패 보고)
```

진행 중에 막히는 부분이 있으면 블로커(작업을 진행할 수 없게 만드는 장애물)를 생성해서 사람에게 알립니다. 댓글도 달고, 새 이슈도 만듭니다.

이 작업 흐름 전체가 WebSocket(서버와 클라이언트가 지속적으로 양방향 통신하는 프로토콜)을 통해 실시간으로 스트리밍됩니다. 에이전트가 무엇을 하고 있는지 대시보드에서 바로 확인할 수 있습니다.

## 4. 8개 런타임을 하나로 묶는다

현재 코딩 에이전트 시장은 빠르게 분화하고 있습니다. Anthropic의 Claude Code, OpenAI의 Codex, Google의 Gemini CLI, 그리고 OpenClaw, OpenCode, Hermes, Pi, Cursor Agent까지. 각각 장단점이 다르고, 잘 하는 작업도 다릅니다.

### 벤더 종속 없는 통합 관리

Multica는 이 8개 런타임을 하나의 플랫폼에서 통합 관리합니다. 로컬 머신에 데몬(백그라운드에서 지속적으로 실행되는 프로세스)을 설치하면, 데몬이 PATH(운영체제가 실행 파일을 찾는 경로 목록)에 있는 에이전트 CLI를 자동으로 감지합니다.

- Claude Code가 설치되어 있으면 Claude Code용 런타임이 등록됩니다
- Codex가 있으면 Codex 런타임이 추가됩니다

이 설계가 중요한 이유는 벤더 종속을 피할 수 있기 때문입니다. 특정 작업에는 Claude Code가 낫고, 다른 작업에는 Codex가 나을 수 있습니다. Multica를 쓰면 하나의 대시보드에서 여러 에이전트를 작업 성격에 맞게 배치할 수 있습니다.

### 지원 에이전트 목록

| 에이전트 | 제공사 |
|----------|--------|
| Claude Code | Anthropic |
| Codex CLI | OpenAI |
| Gemini CLI | Google |
| Cursor Agent | Cursor |
| OpenClaw | 오픈소스 |
| OpenCode | 오픈소스 |
| Hermes | 오픈소스 |
| Pi | Inflection |

## 5. 스킬 시스템: 에이전트의 경험이 축적된다

Multica에서 가장 눈여겨볼 기능은 스킬(Skill) 시스템입니다.

### 문제: 에이전트의 경험 휘발

일반적으로 AI 에이전트는 작업을 하고 나면 그 경험이 사라집니다. 같은 종류의 배포 작업을 열 번 시키면 열 번 다 처음부터 합니다.

### 해결: Compound Skills (복리형 스킬 축적)

Multica의 스킬 시스템은 이 문제를 해결합니다. 에이전트가 한번 해결한 작업은 코드, 설정, 컨텍스트를 포함한 재사용 가능한 스킬 정의(skill definition)로 저장됩니다.

- 배포 스크립트 작성
- DB 마이그레이션
- 코드 리뷰 패턴
- 테스트 코드 생성 등

한번 만들어진 스킬은 팀의 모든 에이전트가 사용할 수 있습니다. A 에이전트가 만든 배포 스킬을 B 에이전트도 실행할 수 있습니다. 시간이 갈수록 팀의 스킬 라이브러리가 쌓이면서, 에이전트들의 역량이 복리처럼 누적됩니다. Multica 측에서 "compound skills"라는 표현을 쓰는 이유입니다.

### 왜 중요한가?

이것은 단순한 편의 기능이 아닙니다. 사람 팀에서도 신입이 들어오면 기존 팀원의 노하우를 흡수하면서 빠르게 적응하는데, 에이전트에게도 같은 구조를 만들어주는 것입니다. 에이전트를 새로 추가해도 기존 스킬 라이브러리를 그대로 활용할 수 있으니 온보딩 비용이 거의 없습니다.

## 6. 아키텍처: 코드는 내 머신에서 실행된다

보안에 민감한 팀이라면 가장 먼저 궁금한 것이 "코드가 어디서 실행되느냐"일 것입니다.

### 보안 원칙

Multica의 아키텍처는 이 점을 명확히 분리합니다.

- 코드 실행: 반드시 사용자의 로컬 머신이나 사용자가 통제하는 인프라에서 이루어집니다
- Multica 서버를 통과하는 것: 작업 상태와 이벤트 데이터뿐입니다
- 소스코드가 외부 서버로 나가지 않습니다

### 시스템 구조

```
┌──────────────┐     ┌──────────────┐     ┌──────────────────┐
│   Next.js    │────▶│  Go Backend  │────▶│   PostgreSQL     │
│   Frontend   │◀────│  (Chi + WS)  │◀────│   (pgvector)     │
└──────────────┘     └──────┬───────┘     └──────────────────┘
                            │
                     ┌──────┴───────┐
                     │ Agent Daemon │  ◀── 로컬 머신에서 실행
                     └──────────────┘
```

### 기술 스택 상세

| 계층 | 기술 | 설명 |
|------|------|------|
| Frontend | Next.js 16 | App Router 기반 |
| Backend | Go (Chi 라우터) | sqlc로 타입 안전 쿼리 |
| Database | PostgreSQL 17 | pgvector 확장 포함 (스킬 유사도 검색용) |
| 실시간 통신 | gorilla/websocket | 에이전트 상태 스트리밍 |

### 코드베이스 구성

- TypeScript: 53.4%
- Go: 43.0%
- 프론트엔드와 백엔드가 거의 반반입니다

### GitHub 지표

- 스타: 16,300개+
- 포크: 2,000개
- 릴리스: 43회 (최신 v0.2.6)

## 7. Paperclip과의 차이: 팀 협업 vs 1인 시뮬레이션

비슷한 공간에 Paperclip이라는 프로젝트가 있습니다. 두 프로젝트를 비교하면 Multica의 설계 철학이 더 선명해집니다.

| 구분 | Multica | Paperclip |
|------|---------|-----------|
| 컨셉 | 기존 개발팀에 에이전트를 팀원으로 합류 | AI 에이전트 회사 시뮬레이터 |
| 사용자 모델 | 여러 사람이 역할/권한을 나눠 가짐 | 한 명의 운영자가 에이전트 군단 지휘 |
| 거버넌스 | 가벼운 프로젝트 관리 (이슈, 프로젝트, 레이블) | 무거운 체계 (조직도, 승인 프로세스, 예산 관리) |
| 실행 환경 | 클라우드 퍼스트 | 로컬 실행 중심 |
| 협업 구조 | 에이전트와 사람이 같은 보드 위에서 협업 | 혼자서 에이전트 팀 운용 |

이 차이는 결국 "에이전트를 누가 쓰느냐"에 대한 가정이 다른 데서 비롯됩니다. 대부분의 실제 개발팀에게는 Multica의 접근 방식이 더 자연스러운 진입점일 것입니다.

## 8. 시작하기: 4단계로 첫 작업 할당까지

실제로 Multica를 써보려면 네 단계만 거치면 됩니다.

### Step 1: CLI 설치 및 데몬 시작

macOS/Linux (Homebrew):
```bash
brew install multica-ai/tap/multica
multica setup
```

curl 기반 설치:
```bash
curl -fsSL https://get.multica.ai | sh
multica setup
```

`multica setup` 명령 하나로 인증, 설정, 데몬 시작이 한번에 처리됩니다.

### Step 2: 런타임 확인

웹 앱에서 Settings > Runtimes로 이동해 자신의 머신이 활성 런타임으로 등록되었는지 확인합니다.

### Step 3: 에이전트 생성

Settings > Agents에서 새 에이전트를 만듭니다.

- 연결할 런타임 선택
- 프로바이더 선택 (Claude Code, Codex 등)
- 이름 부여 (이 이름이 보드와 댓글에 표시됩니다)

### Step 4: 이슈 할당

이슈를 만들고 에이전트에게 할당합니다. CLI로도 가능합니다.

```bash
multica issue create
```

에이전트가 자동으로 작업을 가져가서 실행하고, 진행 상황을 실시간으로 보고합니다.

### 셀프호스팅

셀프호스팅을 원한다면 Docker가 필요합니다.

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash -s -- --with-server
multica setup self-host
```

## 9. 주요 기능 상세

### 9.1 태스크 라이프사이클 관리

태스크는 다음 상태를 거칩니다.

```
enqueue → claim → start → complete (또는 fail)
```

각 단계에서 태스크가 어디에 있는지 명확하게 확인할 수 있어, "결과물이 나오길 기대하며 기다리는" 것이 아니라 실시간으로 진행 상황을 추적할 수 있습니다.

### 9.2 모니터링 및 제어

| 기능 | 설명 |
|------|------|
| Execution Logs | 모든 도구 호출과 명령어를 타임스탬프와 함께 리플레이 |
| Live Steering | 실행 중인 에이전트에게 메시지 전송 |
| Usage Analytics | 에이전트별, 이슈별 비용 추적 |
| Review Gates | 머지 전 사람의 승인 필수화 |
| Inbox | 에이전트 개입이 필요할 때만 알림 |

### 9.3 자동화 기능 (Autopilots)

스케줄링된 태스크를 자동으로 실행합니다.

- 일일 스탠드업 보고서
- 정기 감사
- 자동 리포트 생성

### 9.4 멀티 워크스페이스

- 여러 에이전트를 서로 다른 런타임에서 동시에 실행할 수 있습니다
- 워크스페이스 단위로 격리하여 이슈, 에이전트, 설정을 독립적으로 관리합니다
- Squad 기능으로 에이전트와 사람을 그룹화하여 조율된 협업을 수행할 수 있습니다

## 11. 언제 Multica를 사용해야 할까?

### 적합한 경우

- 팀 단위로 여러 에이전트를 조율해야 할 때
- 여러 프로젝트에 걸쳐 에이전트 작업을 추적해야 할 때
- 에이전트의 솔루션을 팀 지식으로 축적하고 싶을 때
- 자동화된 워크플로우 (일일 감사, 리포트 등)가 필요할 때

### 덜 적합한 경우

- 간헐적으로 단일 에이전트만 사용하는 솔로 개발자
- 단순 CLI 직접 실행으로 충분한 간단한 태스크

## 13. 핵심통찰

Multica가 보여주는 진짜 흐름은 "더 똑똑한 에이전트를 만드는 것"이 아니라 "이미 있는 에이전트들을 조직적으로 운용하는 인프라를 만드는 것"입니다.

코딩 에이전트가 하나일 때는 프롬프트만 잘 쓰면 됐지만, 여럿이 되면 작업 배분, 상태 추적, 경험 공유라는 전통적인 팀 관리 문제가 고스란히 돌아옵니다.

아직 v0.2.6의 초기 단계이고, 스킬 시스템의 실제 품질이나 대규모 팀에서의 안정성은 검증이 더 필요합니다. 그러나 에이전트 수가 늘어나는 추세가 확실한 이상, "에이전트 관리 플랫폼"이라는 계층이 필요해지는 것도 시간 문제입니다.

Multica는 그 방향의 가장 앞선 오픈소스 시도 중 하나로, 에이전트를 단순한 도구가 아닌 관리 대상으로 바라보는 시각 전환을 보여주고 있습니다.
